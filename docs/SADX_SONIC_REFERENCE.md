# SADX Sonic (GameCube): what is known about the original player

One consolidated reference for the original SADX Sonic, like `docs/STH2005_PLAYER_REFERENCE.md` is for Shadow. Every fact carries its evidence: **decompile** (Ghidra pseudocode of `_Main.rel`, `sadxDecomp/decompiled/pseudocode.c`, address = 0x80400000 + file offset; Gekko paired-single math is missing there), **dump** (the RAM dump `sadxDecomp/mem1.raw`, Emerald Coast act 1, Sonic at rest, read 2026-10-07), **hypothesis**, **unknown**. Nothing here was measured live yet. Compact twin: `docs/ai/SADX_SONIC.md`.

## The task and its structs (2026-10-07)
- Sonic's task has the exec, display and destroy pointers at +0x10 / +0x14 / +0x18 = `FUN_805af2b0`, `FUN_805a9f90`, `FUN_805aa5fc` (decompile; `FUN_805af2b0` case 0 stores the last two). They lie 0x5320 and 0x4CB4 below the exec function, so (exec, exec-0x5320, exec-0x4CB4) side by side is a signature that works without the module's load address. Dump: one match, task 0x807af2f8, pointers 0x8047B2F0 / 0x80475FD0 / 0x8047663C (module at 0x802CC040 by the object-list method of `tools/sadxLiveTasks.py`, which gives the same exec address).
- Task +0x20 = **w1** (the entity), +0x24 = **w2** (the movement block); **w3** = the word at w2+0x00 (pointer). Dump: w1 0x807e3420, w2 0x807e34e0, w3 0x807e3da0.
- **w1** (decompile + dump): +0x00 u8 action = the state (the switch in `FUN_805af2b0`; 0 init, then 1; 'V' 0x56 / 'W' 0x57 are forced by `FUN_8044764c`; the case numbers are named in "Action numbers" below), +0x01 u8 (decompile, `FUN_805a6004`: the action an object asks for: 1 gives case 3, 2 case 7, 3 and 8 case 9, 4 case 0xA, 5 case 0xB, 6 and 7 case 9 with other animations, 9 and 10 case 0x14), +0x04 u16 status flags (0x100 ball, 0x2000, 0x4000 read in the steering and speed code, 0x20 / 0x02 near the top of the main function), +0x08 u8 character index (0 = Sonic), +0x14 / +0x18 / +0x1c 32 bit rotation x / y / z in 16 bit angles (y = heading, dump 0x3f8d), +0x20 / +0x24 / +0x28 position floats (dump (-649.41, 4.0, 682.72)), +0x2c.. scale 1.0, +0x38 pointer to the collision record (`FUN_8041e728` target; its +0xa2 / +0xa4 hold the ground contact in the speed code).
- **w2** (decompile + dump): +0x04 / +0x08 / +0x0c = velocity per frame (`FUN_804dac14` writes `speed * direction` into +0x04 and +0x0c; dump (0.032, -0.080, 2.868); hypothesis: world axes), +0x10.. acceleration (hypothesis), +0x20 u16 the heading the stick asks for (`FUN_804de8a0` copies the stick angle into it before `FUN_804dd3f8` turns the heading towards it).
- **w3** (decompile + dump): +0x38 forward speed per frame (dump 2.8681, equals w2's z), +0x3c / +0x40 other local speed components (hypothesis; `FUN_804dac14` zeroes all three when it sees a wall in front), +0x5c / +0x60 u32 flags (0x20000, 0x4000 choose the other accel functions), +0x7e u16 counter bumped each frame while status 0x100 is set, +0x9c.. the per-character physics record (33 words copied from `_Main` 0x2C61E8; dump +0xa0 2.0, +0xa4 16.0, +0xa8 16.0, +0xac 3.0, +0xb4 1.66 jump speed, +0xc4 1.39 run speed, +0xd8 0.05 ground accel, +0xdc 0.031 air accel, +0xe0 -0.06 ground decel, +0xf4 -0.01, +0x10c collision size 4.0, +0x114 gravity 0.08, +0x11c center height 5.4; the meanings are those of the comments in `Scripts/sadx/player.lua`, offsets there are relative to the record = w3 - 0x9c), +0x64 pointer (unknown block).

## Address spaces (decoded 2026-10-10; decompile + dump)
- The decompile's image places the module's sections one after another from 0x80400000 and puts the **BSS after the file** (`tools/decomp/sadx/buildRelImage.py`: sec6 = 0x8086C840, size 0x1E3E00). At run time the loader puts the code/data sections at **decompile address - 0x133FC0** (dump: exec 0x8047B2F0) and allocates the BSS **separately: decompile address - 0x1FF860** (dump; BSS start 0x8066CFE0). So `DAT_8094xxxx`, `DAT_808bxxxx`, `DAT_809axxxx` of the decompile are BSS and must be shifted by 0x1FF860, not 0x133FC0. How found: the relocated instructions of `FUN_804799ec` (dump 0x80345a58 / 0x80345a64) load decompile address 0x8094C110 as `lis r6,0x8075 / addi r6,r6,0xc8b0` = 0x8074C8B0.
- DOL globals (`vi_count` 0x800C44E4) are absolute. The BSS shift is a property of this build/run (the loader's allocation); `tools/sadxLiveLog.py` recomputes it from those two instruction words.
- **Corrects** the 2026-10-07 text below: the dump values "stick 0 / camera null / pad zeros" were read at the unshifted addresses (wrong place). Shifted, the dump holds the data (next section).

## Input (2026-10-07, corrected 2026-10-10)
- **The game's processed stick** (decompile `FUN_804799ec` writes, `FUN_804e6230` reads; BSS 0x8094C330 + 8 x character index): u32 angle and float magnitude at +4. `FUN_804799ec` takes the pad's main stick x / y (pad record +0x1c / +0x1e, s16 = signed byte << 8), subtracts a dead zone of 3072 (constants `DAT_80616184` / `88`), takes `atan2` (`FUN_804019fc`) and subtracts the camera entity's yaw (`+0x18`; when the camera pointer is null no subtraction), so **the angle is the stick's direction in the world, the camera applied**. Magnitude = (length / 29440)^3 (`DAT_806161a0` = 2.5519e13, cubic response), capped at 1.0 (`DAT_806161a4`). Observed on the dump (corrected address): angle 0x3f8d = Sonic's heading, magnitude 0.9999; pad y -127 (stick forward), camera yaw 0x8073: 0xC000 - 0x8073 = 0x3F8D, so forward on the stick is 0xC000 before the camera. `FUN_804de8a0` uses it as the target heading without the camera again.
- `FUN_804e6230` returns 0 (no input) when the magnitude is 0.0 (apart from a special case with status 0x100 and a stage id of 0x902 / 0x903), or when the short at +10 of the per-player block (table at BSS 0x809A7AA0; entry 0 = w3 itself on the dump, so the short is `w3+0xa`, 0 there) is non-zero and status 0x2000 is clear (hypothesis for `w3+0xa`: input locked). Stage id (decompile) = `DAT_8094a026 << 8 | DAT_8094a024`: dump 0x0100 (Emerald Coast act 1). Gravity direction `DAT_8094a048` = (0, -1, 0) on the dump.
- **Pad record** (decompile `FUN_80479cbc` copies the block that `*(BSS 0x8094C510)` points to; replay/demo paths `FUN_8045e8cc`, `FUN_8045e9d4`, `FUN_8045ead8` fill the same words): BSS 0x8094C370 + 0x34 x character index. +0x08 buttons held (= `DAT_8094c378`; the replay paths OR in bit 8), +0x0c its complement, +0x10 pressed this frame (held & ~previous, `DAT_8094c380`), +0x14 released, +0x18 / +0x1a u16 0..255 (hypothesis: analog L / R triggers: the free camera adds them), +0x1c / +0x1e s16 main stick x / y (dump y = -127 = forward; `FUN_804799ec`), +0x2c the previous frame's held word (`DAT_8094c39c`). The no-pad default writes held 0, complement 0xffffffff (the dump's `0xffffffff` at +0x0c). Button masks (module data, dump): jump 0x4 (`DAT_8069ab84`), action 0x402 (`DAT_8069ab80` / `90`); Dreamcast bit convention (hypothesis): 0x4 A, 0x2 B, 0x400 X. The dump's held word is 0 although the stick is full: running needs no button.
- **Camera** (decompile, dump): the camera entity pointer is BSS 0x808B3D10 (dump 0x807E3240): +0x14 rotation x (dump -1244), +0x18 rotation y = yaw (dump 0x8073), +0x20 / +0x24 / +0x28 position = the eye (-650.21, 39.0, 609.86 on the dump). The module-data pointer `PTR_DAT_80614a1c` (dump 0x806B4960) names the camera output block: +0x08 float 50.0 (hypothesis: field of view), +0x0c eye, +0x18 look-at (dump (-649.44, 30.61, 679.86): 70 in front of the eye along +z, 8.4 below it and 26.6 above Sonic's position (y 4.0); hypothesis: the player's position plus a height offset, `FUN_80429edc`), +0x24 / +0x28 angles (0 on the dump); `FUN_80429e40` / `FUN_80429edc` write it from the entity. The camera's own modes are not read.

## Ground contact: where "on the floor" is decided (2026-10-10; decompile `sadxDecomp/decompiled/pseudocode.c`, dump values from `sadxDecomp/mem1.raw`; nothing run)
Supersedes the earlier "decision NOT found" (second port run, last bullet). Evidence: decompile unless marked. The earlier ruled-out functions stay ruled out.
- **Who sets the bit.** `FUN_804dac14` (movement step, called every frame of the action chain) calls `FUN_804d8ccc(w1, w2, w3)` (7924 bytes, lines 218652-219636; stage 0x902/0x903 call `FUN_804d1fa4` instead, not read). `FUN_804d8ccc` clears w1+4 bit 0x1 at its start (line 218773, after saving the previous status in w3+0x10, and the one before in a local), and sets it again only in the floor branch (lines 219566 and 219586, `| 1`) together with `FUN_804d6f08(.., hit flags)`, which ORs the hit's surface flags into w3+0x5c and resets w3+0x114/0xf4/0xd8 from the character record. Status bit 0x2 is not set here (not found yet). So "grounded" = this step's sweep found a floor hit; there is no separate floor ray.
- **Shape and size.** A swept SPHERE kept in a struct pointed to by w3+0x64 (M: 0x807e4060): `[0]` radius = **0.5 x w3+0x110** (record +0x74 = 10.0, so **5.0**; M 5.0), `[1..3]` centre = task position + (0, **5.0**, 0) rotated by the player's orientation (M: task y 4.00, centre y 9.00, so the sphere's lowest point is the task position = the feet), `[4..6]` the step's displacement (w2+4..0xc, includes the per-frame gravity, see below). It is NOT w3+0x10c (4.0) or w3+0x11c (5.4): `FUN_804d8ccc` never reads them (grep); they belong to the object distance test and probe/camera readers recorded above.
- **The test (`FUN_8043d5a0`, per collision group, 476 lines).** Candidates come from `FUN_8043fe48` (broadphase: groups within radius + |step|, up to 0x80 triangles). For each triangle the sphere centre is sampled at the start, every 0.5 x radius (2.5) along the displacement, and at the end; each sample point is moved into the triangle's frame (plane = height 0) and counts as a hit when |height| <= radius AND the point's projection onto the plane lies inside the triangle (three same-sign edge cross products). There is NO edge or vertex case: a sphere that only touches an edge or a corner is not a hit. Triangle flag 0x800000: normal flipped to face the centre. Up to 16 hits are collected and the one with the smallest value at hit entry +0x98 is the result (H: path parameter). Result block: `[0xd/0xe]` angles from the normal, `[0x12..0x14]` the triangle's FACE normal, `[0x15..0x1a]`, `[0x1b..0x1d]` contact point and offset.

## Motion blending (2026-10-11; decompile `FUN_804cf4f4` and `FUN_804cea34` in `sadxDecomp/decompiled/pseudocode.c`; nothing run; ported 2026-10-11, see the last item)
The original SADX blends between motions. Evidence: decompile only (external); the length of the blend per motion comes from the table entry's +8 (see the twin's id list), not seen in a recording.
- **Struct** (`param_1` of `FUN_804cf4f4` = w3+0x120): +0 mode, +4 new id, +6 id of the last step, +0x10 float32 frame / blend factor (the same slot), +0x14 float32 "frame2", +0x20 table. Table entry (0x10 B): +0 ptr to the motion, +4 node count, +5 mode, +6 next id, +8 float32 blend step, +0xc float32 rate.
- **Start** (mode 1, runs the step the id changed, `FUN_804cf4f4` lines 213150-213170): if the new entry's blend step is exactly 1.0 or the two entries use different models (`**entry` differs), no blend: the new motion starts at frame 0 (mode 2 then adds the step 1.0 >= 1.0 at once). Otherwise `FUN_804cea34` builds a transition motion, then the mode becomes 2 (blend).
- **The transition motion** (`FUN_804cea34`, per node, position/rotation/scale each as 2 keys): key 0 = the OLD motion sampled at its current frame (the frame slot's value when the id changed; linear between its keys; rotations by the short way), key 1 = the NEW motion's first key (frame 0 values). Nodes the new motion doesn't key use the model's rest values. If either motion has bit 2 of its type word (`(motion+8) >> 2 & 1`; hypothesis: NJD_MTYPE_SCL_2, the scale channel set, the nodes then have 3 channel pointers) the scale set is built too, and the transition's type word is 7 (else 3). The transition is a fresh 2-key motion played by the same draw.
- **Mode 2** (blend): each step the factor (+8) += the table's blend step (+8 of the NEW entry); at >= 1.0 the mode becomes the entry's own mode (+5), the transition's buffers are freed, and the frame is set to 0, or for the modes 3, 9, 10, 0xc to the "frame2" slot (+0x14, which is then zeroed). So during the blend the new motion's pose is held at its FIRST key (it doesn't advance), and after it the motion starts from frame 0 (loops: frame2). With step s the blend lasts ceil(1/s) steps (0.25: 4; 1/16: 16).
- **Table steps** (RAM dump `sadxDecomp/mem1.raw` at 0x80620520, entry +8, read 2026-10-11 by a scratchpad script; external, dump): stand 0x0 1/16; walk 0x9, speedwalk 0xa, jog 0xb, run 0xc 0.25; sprint 0xd 0.5; jump 0xe and roll 0xf 0.25 (both point at the same motion data); springFall 0x11 0.125; fall 0x12 0.25; landing 0x13 1.0; brake 0x14 0.25; damage 0x17 1.0; turnAround 0x1e 1.0; ball 0x20 0.5.
